> 调研时间：2026-10-23（Asia/Shanghai）
> 范围：Claude Code、Codex CLI、dsh；补充 QoderWork、WorkBuddy、AgentMore、千问办公、扣子、飞书 Aily、MiniMax Agent。

## 0. 一屏结论

| Agent | 能否删掉单条消息并成功恢复 | 一句话结论 |
|---|---|---|
| **Claude Code 2.1.309** | **能（需跨存储清理）** | JSONL 是 `parentUuid` 链；删掉目标 user/assistant 条目并把子条目的 `parentUuid` 接回祖先后，`--resume` 成功，模型看不到暗号。但必须同时清掉 `history.jsonl`、auto-memory、file-history 等会话外副本；只改 JSONL 不够。 |
| **dsh 0.2.1-rc.2** | **有条件（不能安全地物理删行）** | 会话是 `seq` 连续的事件流，没有 `parentUuid`。直接删行/重排 `seq` 会触发 inbox 重放，把旧提问重新跑一遍；把目标事件的**内容字段抹空、保留 seq** 后恢复成功，模型看不到暗号。dsh 没有删除 API，原生做法是 compaction/`surfaceOp: replace`，不是真正擦除。 |
| **Codex CLI 0.164.0** | **有条件（未实测）** | rollout JSONL 按行顺序恢复，没有 `parentUuid`；删普通 `response_item` 行通常可恢复，但 `compacted.replacement_history` 会原样重放压缩后的完整历史，必须连同它一起改。没有本机 CLI，未做恢复实验。 |
| **扣子 Coze** | **云 API 支持删除消息；Studio 实为按 run 软删** | 服务端会话，消息保存 180 天；云 API 有删除消息接口。但开源 Studio 的 `DeleteMessage` 会删掉该消息所属 run 的整组消息并标 `status=2`，不是单行物理删。 |
| **其他国内平台** | **本轮已挖到真结果，但都不支持已证的单条删除** | QoderWork 没有用户级单条删除（JSONL 正文 + SQLite 投影，删 DB 可被 transcript 补回）；WorkBuddy 只有会话级删除 API；QwenWork 与 Qoder 同源；飞书 Aily 只有删会话；MiniMax 代码提供会话级物理删；AgentMore 只有 `conversation/delete`。详见 [调研结果-02-国内平台.md](调研结果-02-国内平台.md)。 |

## 1. 任务 A：会话格式调研

### 1.1 Claude Code 2.1.309

**版本来源**：本机安装的 `claude --version` 输出 `2.1.309 (Claude Code)`。

#### 会话文件位置

| 平台 | 位置 |
|---|---|
| Windows | `%USERPROFILE%\.claude\projects\<cwd 编码>\<session-id>.jsonl` |
| macOS | `~/.claude/projects/<cwd 编码>/<session-id>.jsonl` |
| Linux | `~/.claude/projects/<cwd 编码>/<session-id>.jsonl` |

- `<cwd 编码>` 是工作目录路径中非字母数字字符替换成 `-`；超过 200 字符会截断并加路径哈希。[文档](https://code.claude.com/docs/en/sessions)
- `CLAUDE_CONFIG_DIR` 可以把整个 `~/.claude` 搬走；`CLAUDE_CODE_PROJECT_DIR_NAME` 可以自定项目目录名。[文档](https://code.claude.com/docs/en/sessions)
- 一个会话默认对应 **1 个主 JSONL**；子代理另有 `projects/<project>/<session-id>/subagents/*.jsonl`，大工具输出在 `tool-results/`。[文档](https://code.claude.com/docs/en/claude-directory)
- 本次实验的会话是 53 行、60,272 bytes 的单个 JSONL。[实验]

#### 文件格式与条目类型

**格式**：JSONL，一行一个 JSON 对象。官方明确说这是内部格式，跨版本可能变化，不建议脚本直接依赖。[文档](https://code.claude.com/docs/en/sessions)

本次短会话（5 轮、未压缩）观察到 15 种 `type`：

| type | 主要字段（脱敏） | 作用 |
|---|---|---|
| `user` | `parentUuid,isSidechain,promptId,type,message,uuid,timestamp,permissionMode,origin,promptSource,turnOrigin,turnPosition,userType,entrypoint,cwd,sessionId,version,gitBranch` | 用户消息；工具结果也以 `user` + `message.content[].type=tool_result` 出现 |
| `assistant` | `parentUuid,isSidechain,message,thinkingDurationMs,thinkingDisplay,serverClassifierRequest,apiBlockIndex,requestRef,requestedModel,type,uuid,timestamp,effort,perTurnEffort,session_id,...` | 模型消息；一个回合可能拆成 thinking / text / tool_use 多条 |
| `attachment` | `parentUuid,isSidechain,attachment,type,uuid,timestamp,rendered,renderedRole,...` | 附件、记忆、上下文注入 |
| `system` | `parentUuid,isSidechain,type,subtype,durationMs,messageCount,timestamp,uuid,isMeta,...` | 回合/步骤系统事件 |
| `api-request` | `type,sessionId,id,timestamp,version,querySource,shapeHash,params,base,keep,tail,cacheControl,requestDigest` | API 请求审计记录 |
| `api-request-blob` | `type,sessionId,hash,message` | 请求里的消息块副本 |
| `api-request-shape` | `type,sessionId,shapeHash,timestamp,version,shape` | 请求形状 |
| `last-prompt` | `type,lastPrompt,leafUuid,sessionId` | 最近一次输入 + 当前叶子 UUID |
| `ai-title` | `type,aiTitle,sessionId` | 自动标题 |
| `mode` | `type,mode,sessionId` | 模式切换 |
| `permission-mode` | `type,permissionMode,sessionId` | 权限模式 |
| `atis-latch` | `type,atis,sessionId` | 内部状态闩 |
| `file-history-snapshot` | `type,messageId,snapshot,isSnapshotUpdate` | 文件快照元数据 |
| `file-history-delta` | `type,messageId,snapshotMessageId,trackingPath,backup,timestamp` | 文件快照增量 |
| `cost-state` | `type,sessionId,totalCostUSD,totalAPIDuration,...,modelUsage` | 成本统计 |

脱敏样例（只保留结构）：

```json
{"type":"user","uuid":"<uuid>","parentUuid":"<uuid>","message":{"role":"user","content":[{"type":"text","text":"<text>"}]},"sessionId":"<uuid>","cwd":"<cwd>","version":"<version>"}
{"type":"assistant","uuid":"<uuid>","parentUuid":"<uuid>","message":{"role":"assistant","content":[{"type":"thinking","thinking":"<text>"},{"type":"text","text":"<text>"}]},"sessionId":"<uuid>","cwd":"<cwd>","version":"<version>"}
{"type":"last-prompt","lastPrompt":"<text>","leafUuid":"<uuid>","sessionId":"<uuid>"}
```

#### 消息怎么串起来；删中间一条会不会断链

- 主链是 `parentUuid -> uuid`，`last-prompt.leafUuid` 指向当前叶子。[本机观察]
- 会话不是“一条消息一行”这么简单：一个回合会有多条 `assistant`（thinking / text / tool_use）和 `user`（tool_result），所以删“模型对它的回复”通常要删多行。
- 删除中间条目必然产生“子条目的 parentUuid 指向已删 uuid”的断链。修复方式是沿被删节点的 parent 往上找最近的保留祖先，把子条目的 `parentUuid` 改过去；如果被删的是叶子，还要改 `last-prompt.leafUuid`。
- 同一 JSONL 内还可能有多份副本：`api-request-blob.message`、`api-request.params`、`file-history-snapshot/delta` 的 `snapshot` 都可能带正文或正文引用；删主消息后要做全文扫描，不能只按 `type=user/assistant` 过滤。[本机观察 + 第一次工具会话实验]
- 本次实验删了 5 条（`user`、`last-prompt`、3 条 `assistant`），只改了两处 `parentUuid`：
  - `system` 条目（uuid `<uuid-A>`）的 `parentUuid`：由被删的 assistant 改为保留的 `system`（uuid `<uuid-B>`）。
  - `assistant` 条目（uuid `<uuid-C>`）的 `parentUuid`：由被删的 assistant（uuid `<uuid-D>`）改为保留的 `user`（uuid `<uuid-E>`）。
  - 另外删掉了 `last-prompt`，它的 `leafUuid` 原本指向被删的 user。[实验]

#### 压缩（compact / summary）之后怎么存

- 文档：`/compact` 用摘要替换历史；恢复时如果该会话被压缩过，会从 “Conversation compacted” 行开始，加载最后一次 compaction 的 summary、未摘要的消息和之后的消息，**被摘要的旧消息不会再次加载**。[文档](https://code.claude.com/docs/en/sessions)
- 文档：`/rewind` 的 “Summarize” 明确说“original messages stay in the session transcript”，摘要只改变上下文，不删除原始消息。[文档](https://code.claude.com/docs/en/checkpointing)
- 本次 5 轮短会话没有触发 compaction，所以“压缩摘要在 JSONL 里具体是哪个 type、哪些字段”**未确认**；不能把文档的语义直接当成条目结构。

#### 恢复（resume / continue）读哪些文件、有没有校验

- `claude --resume <id>` / `--continue` 读 `projects/<project>/<session-id>.jsonl`；`--resume <transcript-path>` 可以直接指定绝对路径。[文档](https://code.claude.com/docs/en/sessions)
- 本机实测：`claude -p --resume <id>` 能读取一个**手工改过**的会话并成功回答；没有报 hash、签名、计数错误。JSONL 里没有看到签名/哈希字段；只有 `version` 这种版本标记。[实验]
- 恢复会恢复消息、工具调用/结果、模型、agent、权限模式等；压缩后的会话从 compaction 行开始。[文档](https://code.claude.com/docs/en/sessions)
- `api-request` / `api-request-blob` 是审计/重放记录，不是恢复模型历史的唯一来源；本次删掉含暗号的 user/assistant 后，恢复没有因为它们报错。[实验]

#### 正在运行的会话会不会重新读文件

- 会话是持续追加写；恢复是启动时读 JSONL，不是每一轮重新扫文件。[文档](https://code.claude.com/docs/en/sessions) + [本机观察]
- 运行中直接改 JSONL **不应期待生效**：已加载的会话在内存里，追加写还会覆盖/接续；本次没有在运行中实测，只做了退出后改文件再 resume。[未确认：运行中改文件的行为未实测]
- 同一会话在两个终端 resume 而不 fork，消息会交错写进同一个 transcript。[文档](https://code.claude.com/docs/en/sessions)

#### 会话之外，还可能留着同一段内容的地方

这次实验非常具体地撞上了几个：

| 位置 | 说明 | 来源 |
|---|---|---|
| `~/.claude/history.jsonl` | 用户输入历史，含 prompt 文本、时间、项目路径 | [文档](https://code.claude.com/docs/en/claude-directory)；本次合成暗号也出现在这里 [实验] |
| `~/.claude/projects/<project>/memory/` | auto-memory：模型自己写的长期记忆 Markdown（`MEMORY.md`、主题文件） | [文档](https://code.claude.com/docs/en/claude-directory)；本次模型自行写了 `secret-passphrase.md` 和 `MEMORY.md` [实验] |
| `~/.claude/file-history/<session>/` | 文件编辑前的快照，供 `/rewind` 恢复 | [文档](https://code.claude.com/docs/en/checkpointing)；本次工具会话产生过含暗号的快照 [实验] |

| `~/.claude/plans/`、`tasks/`、`shell-snapshots/`、`paste-cache/`、`uploads/`、`session-env/`、`debug/`、`usage-data/`、`feedback-bundles/` | 计划、任务、shell 快照、大段粘贴、附件、调试日志、洞察报告、反馈包 | [文档](https://code.claude.com/docs/en/claude-directory) |
| `~/.claude.json` | 项目条目、trust、MCP、UI/账号状态；`projects` 下可能有历史 | [文档](https://code.claude.com/docs/en/claude-directory) |

| 工具产物/工作区文件 | 模型用 Write/Edit/Bash 写出的文件、命令输出、测试日志 | [实验]：模型收到暗号后自行 `Write` 了记忆文件 |
| 调试/监控/反馈 | `--debug` 日志、OpenTelemetry 监控、`/feedback` 的脱敏 transcript 包 | [文档](https://code.claude.com/docs/en/claude-directory)、[监控文档](https://code.claude.com/docs/en/monitoring-usage) |
| 云/远端 | 使用 claude.ai/code、Remote Control、云会话时，服务端另有副本 | [文档](https://code.claude.com/docs/en/sessions) |

#### 保留多久、自动清理的设置项

- `cleanupPeriodDays`：默认 **30 天**，最小 1；设 0 会校验失败。清理 `projects/*.jsonl`、`file-history/`、`plans/`、`debug/`、`paste-cache/`、`uploads/` 等。[文档](https://code.claude.com/docs/en/claude-directory)、[设置项](https://code.claude.com/docs/en/settings-reference#cleanupperioddays)
- `history.jsonl` 默认不在按龄清理范围内（HIPAA 配置例外）；`claude purge <project>` 会按项目删 transcript、auto-memory、tasks/debug/file-history、匹配的 history 行和 `~/.claude.json` 项目条目。[文档](https://code.claude.com/docs/en/claude-directory)
- `CLAUDE_CODE_SKIP_PROMPT_HISTORY` 可以完全抑制 transcript/prompt history 写入；`-p --no-session-persistence` 只抑制单次非交互写入。[文档](https://code.claude.com/docs/en/claude-directory)

#### 有没有官方的“删除 / 回退”能力，粒度是什么

- `/rewind`：按 **prompt/回合** 回退；可选 “Restore code and conversation”“Restore conversation”“Restore code”，还有 “Summarize from here / up to here”。[文档](https://code.claude.com/docs/en/checkpointing)
- `/clear`：开新上下文，旧会话仍保存，可 `/resume` 回去。[文档](https://code.claude.com/docs/en/sessions)
- `/branch` / `--fork-session`：复制会话分支，不改原会话。[文档](https://code.claude.com/docs/en/sessions)
- `claude purge`：按 **项目** 删除 transcript/auto-memory/file-history/history 行等，不是单条消息。[文档](https://code.claude.com/docs/en/claude-directory)
- **没有**官方的“删掉会话里某一条消息”命令；`/rewind` 是回退上下文，不是从 JSONL 抹掉字节。本次实验是直接编辑 JSONL，属于非官方路径。

### 1.2 Codex CLI 0.164.0（源码调研，本机未安装）

**版本**：npm 最新 `@openai/codex` 为 `0.164.0`；本机 `codex` 不在 PATH，**没有跑 `codex --version`**。格式结论来自 `openai/codex` 源码 HEAD `e6ebdfe`，不是本机运行观察。

#### 会话文件位置

| 平台 | 位置 |
|---|---|
| Windows | `%USERPROFILE%\.codex\sessions\YYYY\MM\DD\rollout-<timestamp>-<thread-id>.jsonl`（`CODEX_HOME` 可覆盖根目录） |
| macOS | `~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-<thread-id>.jsonl` |
| Linux | 同上 |

- 目录布局的源码注释：`~/.codex/sessions/YYYY/MM/DD/rollout-YYYY-MM-DDThh-mm-ss-<uuid>.jsonl`。[源码 `codex-rs/rollout/src/list.rs:425`]
- 归档目录 `archived_sessions/`；`SESSIONS_SUBDIR = "sessions"`、`ARCHIVED_SESSIONS_SUBDIR = "archived_sessions"`。[源码 `codex-rs/rollout/src/lib.rs:86-87`]
- `thread/revert` 会保留 thread ID、生成新的 rollout 文件，文件名带 `_<rollout-id>` 后缀。[源码 `codex-rs/rollout/src/recorder.rs:101-103`]
- 一个会话通常对应 **1 个 rollout JSONL**；revert 会产生新的物理文件，旧文件保留。
- 另有全局 `~/.codex/history.jsonl`（用户输入历史）和状态索引/SQLite。`history.jsonl` 记录格式为 `{"session_id":"<uuid>","ts":<unix_seconds>,"text":"<message>"}`。[源码 `codex-rs/message-history/src/lib.rs:1-14, 62-66`]

#### 文件格式与条目类型

**格式**：JSONL；每行是 `RolloutLine`：`{ timestamp, ordinal?, type, payload }`。[源码 `codex-rs/history/src/lib.rs:369-375`]
冷 rollout 可被压缩为 `.jsonl.zst`；读取器透明处理 plain/`.zst`。[源码 `codex-rs/rollout/src/compression.rs:26, 63-67`]

`type` 采用 snake_case，共 12 种：[源码 `codex-rs/history/src/rollout_payload.rs:32-72`]

| type | payload |
|---|---|
| `session_meta` | session/thread id、cwd、originator、cli_version、source、git、instructions 等 |
| `response_item` | 一条 Responses API item：`message` / `reasoning` / `function_call` / `function_call_output` / 自定义工具调用等；可带 `metadata` |
| `compacted` | `message`（摘要）+ `replacement_history`（替换后的完整历史）+ window/resume 元数据 |
| `turn_context` | cwd、approval/sandbox policy、model、effort、summary 等 |
| `event_msg` | `user_message`、`agent_message`、`token_count`、`turn_started`、`turn_complete`、`thread_rolled_back` 等 |
| `token_usage_record` | token 用量 |
| `world_state` | 环境/世界状态快照与 merge patch |
| `security_risk_score` | 安全评分 |
| `retained_context` | 保留的上下文证据 |
| `inter_agent_communication` | 多 agent 通信 |
| `inter_agent_communication_metadata` | 通信元数据 |
| `realtime_item` | 实时展示用的稀疏事实，模型不可见 |

脱敏样例：

```json
{"timestamp":"<ts>","ordinal":0,"type":"session_meta","payload":{"id":"<uuid>","timestamp":"<ts>","cwd":"<cwd>","originator":"<str>","cli_version":"<ver>","source":"cli"}}
{"timestamp":"<ts>","type":"response_item","payload":{"type":"message","role":"user","content":[{"type":"input_text","text":"<text>"}]}}
{"timestamp":"<ts>","type":"compacted","payload":{"message":"<summary>","replacement_history":[{"type":"message","role":"user","content":[{"type":"input_text","text":"<text>"}]}]}}
```

#### 消息怎么串起来；删中间一条会不会断链

- 没有 `parentUuid`。模型历史由 rollout 的**行顺序 + `ordinal`** 重建；工具调用与结果靠 payload 里的 `call_id` 关联，不是条目 uuid。[源码 `codex-rs/core/src/session/rollout_reconstruction.rs` 的重建逻辑]
- 删除普通 `response_item` 行，通常只是让该条消息从重建历史里消失；不会像 Claude 那样出现 parent 断链。但以下情况会“删了还回来”：
  1. 该消息已进入 `compacted.replacement_history`：恢复时 `replacement_history` 被**原样**当作历史；必须同时改 `compacted`。
  2. 该消息在 `thread_rolled_back` 之前的旧轮次：rollback 语义按“最后 N 个 user turn”丢弃，编辑行可能改变 N 的边界。
  3. 文件被状态索引/SQLite 缓存引用：删文件不改索引时，列表可能仍显示旧元数据。
- 本次**没有**做 Codex 删除/恢复实验；以上是源码判断，不是实测。[未确认]

#### 压缩（compact）之后怎么存

- 压缩写入一个 `compacted` 条目，包含 `message` 摘要和可选的 `replacement_history`（`Option<Vec<ResponseItemEnvelope>>`）。[源码 `codex-rs/history/src/lib.rs:290-310`]
- 恢复时反向扫描 rollout，找最新的、带 `replacement_history` 的 `compacted` 作为 checkpoint；历史等于该 `replacement_history` 加上其后的行。[源码 `codex-rs/core/src/session/rollout_reconstruction.rs:290-315, 521-549`]

#### 消息怎么串起来；删中间一条会不会断链

- 主链是 **`seq` 单调递增、无 gap**；没有 `parentUuid`。[源码 `dsh-session-format/README.md:58`、`dsh-session-persistence-jsonl/README.md:57`]
- 消息可见性还受 `surfaceOp` / surface fold 影响；`replace` 可以遮蔽（shadow）旧条目，而不是删行。[源码 `dsh-session/README.md:50, 161`]
- `agent/inbox/spliced` 会**复制** prompt 正文；所以同一句用户话至少可能出现两次：inbox 插入事件 + `user/message`。删 user/message 但漏掉 inbox，仍会漏。[本机观察 + 实验]
- 物理删除一行会制造 `seq` gap；格式层要求 gap-free，恢复时可能丢弃 gap 及其后缀，或者直接拒绝。[源码 `dsh-session-format/README.md:48, 58`]
- 本次先试了“删 seq 22/26/29 + 全部 seq 重编号 + 修 `throughSeq`/`messageSeqs`”，结果恢复时把前面的旧提问当成新 turn 重放（turn 6–9）——说明 inbox 状态不是只靠 `seq` 重编号就能修好。[实验]
- 最终改为**保留 seq、抹空目标事件内容**：`agent/inbox/spliced.data.inserted[0].content[0].text`、`user/message.data.content[0].text`、`assistant/message.data.message.content[0].text`，并清空 `assistant/message.data.stream` 和 `message.source.replayState`。恢复不再重放，暗号命中 0。[实验]

#### 压缩（compact / summary）之后怎么存

- `/compact` 把较老的一段历史替换成一个摘要，保留近期历史；命令生命周期写进 session log，但不进入模型历史。[源码 `dsh-command-compact/README.md:12, 67-69`]
- 会话层设计是 append-only：compaction **隐藏**被取代的条目，不删除原始事件。[源码 `dsh-session/README.md:12`]
- 本次短会话没有触发 compaction；`compacted` 事件的具体 type/字段**未确认**（源码包没有在本次测试中产生实例）。

#### 恢复（resume / continue）读哪些文件、有没有校验

- 读取 `<session-id>` 目录下编号最高的 generation；当前格式走快速路径，历史格式先迁移再恢复。[源码 `dsh-session-persistence-jsonl/README.md:85-87`]
- 校验：header/version、`seq` gap-free、surface 语义、zstd checksum/解压/结构；没有用户签名或内容 hash（zstd frame checksum 只是传输完整性）。[源码 README:77-79, 109-112]
- 崩溃恢复：保留 committed prefix，截断 torn tail；完整 frame 的 checksum/结构错误按 corruption 拒绝。[源码 README:77-79]
- 本次恢复：`dsh --profile headless --session-id ...` 成功，没有报错；模型看不到暗号。[实验]

#### 正在运行的会话会不会重新读文件

- 每个 session 只允许一个 live writer；有内核锁/命名信号量，第二个 writer 被排除。[源码 `dsh-session-persistence-jsonl/README.md:168`]
- 运行中的会话在内存里，事件追加写；不会每轮重读文件。运行中改文件不应期待生效；需要退出后 resume。没有在运行中实测。[未确认]

#### 2.1.5 实验组为什么还会“尝试读记忆文件”

这是本轮最重要的“会话之外”发现，分两件事：

1. **第一次工具会话（非最终实验）**：75 行、15 条 assistant、暗号命中 5 处；模型收到暗号后自行调用了 `Write`，写了一个 `secret-passphrase.md`，并在 `MEMORY.md` 里建立索引；同时 `history.jsonl` 和 `file-history/<session>/` 也留下了副本。这些都不是主 JSONL，但都能让后续会话重新拿到暗号。我们据此清理了测试 home 里的这些副本，并用 **禁用工具** 的方式重建了干净的 5 轮会话。[实验]
2. **干净会话仍然带“指针”**：会话启动时已经注入了指向 `memory/secret-passphrase.md` / `MEMORY.md` 的 attachment/system 元数据。我们删掉了文件，却没有删这些指针；所以实验组模型会“尝试 Read 一个已不存在的记忆文件”，但它**没有拿到暗号内容**。要连“曾经有个暗号文件”都不暴露，还必须清理这些 attachment/记忆指针条目。

结论：**Claude 的“删消息”必须同时删会话外副本，否则暗号会从 memory/history/file-history 漏回来；只删主 JSONL 不足。** 这也解释了为什么一个“删一条消息”的工具，实际要做成“跨存储的定向擦除”。

## 5. 给下一步的结论

1. **Claude Code 的“删一条消息”在技术上可行，但产品必须做跨存储擦除**：transcript + `history.jsonl` + auto-memory + file-history + 可能的 `api-request-blob` / attachment 指针。只改 JSONL 会在真实使用中从 memory 漏回来。
2. **dsh 不适合“物理删行”**：append-only + seq + inbox 的设计决定了安全做法是“内容抹除/compaction/surface replace”，不是删字节。产品如果承诺“文件里也没有”，需要重写 generation 或做 compaction + 新文件，不能只改当前 JSONL。
3. **Codex 的关键坑是 `compacted.replacement_history`**：普通行删掉不等于历史删掉；必须把压缩检查点里的副本一起处理。这个结论来自源码，下一步应装 CLI 做实测。
4. **国内平台里 Coze 是唯一明确支持单条消息删除的**；QoderWork 的消息在三处重复（行、JSON 聚合、FTS），只删一处不够；其余平台大多是云端黑盒，产品上只能做“平台 API 能删就删，不能删就明确告知”。
5. **名字层面**：`unremember` 最干净；`unsay`/`lethe`/`retcon`/`excise` 都有不同程度的同名或同类冲突，其中 `retcon`/`excise` 是直接竞品。
