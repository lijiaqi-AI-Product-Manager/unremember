# 调研结果-02：国内 AI Agent 平台深调（源码 / 数据库 / API 实证）

> 调研时间：2026-10-23
> 对象：QoderWork CN / Qoder CLI、WorkBuddy、千问办公 QwenWork、扣子 Coze、飞书 Aily、MiniMax Code、AgentMore。
> 方法：安装包解包（不改真实数据）、Electron `app.asar` 源码、SQLite schema/只读查询、官方 API 文档、公开仓库源码。所有真实会话只记录结构；路径用 `~` / `%APPDATA%` / `<data-dir>`；不记录内容、密钥、用户名。
> 结论口径：**能物理删**指代码/API 真的删除持久化记录；**能隐藏**指只从模型上下文移除、原始记录仍在。

## 0. 先给硬结论

| 平台 | 本机/源码里到底存哪 | 单条消息能删吗 | 最关键的坑 |
|---|---|---|---|
| **QoderWork CN 0.9.12** | `projects/*.jsonl`（SDK transcript）+ `data/agents.db`（SQLite 投影 + FTS）+ `awareness/` memory | **没有用户级单条删除**；代码只有 assistant 投影删除、按 sequence 截断（retry） | 删 DB 投影不等于删 JSONL；`backfillFromSdkTranscript` 会把 SDK transcript 里“缺的消息”重新补回 DB。删 chat 只软删 DB + 清 memory block，**没找到删 JSONL 的代码** |
| **WorkBuddy 5.8.3.41334564** | `workbuddy.db`（SQLite，sessions 元数据）+ `projects/<cwd>/<session>.jsonl`（transcript） | **会话级**删除 API；没有单条消息删除 API | transcript 是 `parentId`/`logicalParentId` 的分支树，不是简单顺序；删中间要重接父子 |
| **QwenWork 1.4.0.26102214** | 与 QoderWork 同源：`data/agents.db` + `getSessionMessages` SDK transcript（`.qwenworkcn` / `.qoderwork` fallback） | **未发现单条删除**；有 `/compact` 控制命令 | 这是 QoderWork 的换皮/同源实现，Qoder 的“投影可被 transcript 补回”风险同样存在 |
| **扣子 Coze（桌面 1.1.9 / 云 API / Studio）** | 桌面只是 Web wrapper：`%APPDATA%\Coze` 的 IndexedDB/LocalStorage，没有会话 DB；会话在服务端 | **官方有删除消息 API，但 Studio 实现按 run 删整组**（user+assistant），status 软删 | 云侧 180 天自动删除；Studio 的 `DeleteMessage` 先删 `run`，再按 run 把该组消息标 `status=2`，不是单行 |
| **飞书 Aily** | 纯服务端 Session/Message/Run；无本地格式 | **只有删除会话 API，没有删除消息 API** | 会话级 DELETE `/aily/v1/sessions/:id`；消息只有创建/列出/获取；粒度是整会话 |
| **MiniMax Code 0.6.5（开源 CLI）** | `~/.minimax/v2/sessions/...` 的 `messages.jsonl` + SQLite `local_runtime_sessions` / `local_runtime_message_rows` | **代码提供会话级物理删除** `deleteSessionHistory`；没有找到单条消息删除 | 历史是 canonical JSONL + snapshot 链（`compactionSummary` + SHA-256 revision）；删会话目录是真删，删单条不是现成能力 |
| **AgentMore（智谱，云端）** | 纯云端；前端无 IndexedDB（只有 localStorage/sessionStorage） | **只有会话级删除** `conversation_ids`；无消息删除端点 | 多 Agent 群聊/会话；本地没有可改的会话文件 |

## 1. QoderWork CN 0.9.12 / Qoder CLI 1.0.45

### 1.1 两层存储：JSONL 是正文，SQLite 是投影

本机安装的是 **QoderWork CN 0.9.12**（`QoderWork CN.exe` 文件版本 0.9.12）；随包的 `qoderclicn.exe --version` 为 **1.0.45**。

| 层 | Windows | macOS / Linux | 说明 |
|---|---|---|---|
| SDK transcript | `%USERPROFILE%\.qoderworkcn\projects\<encoded-cwd>\<session-id>.jsonl` | `~/.qoderworkcn/projects/...` | 一个会话一个 JSONL；子代理在 `<session-id>/subagents/*.jsonl` |
| SQLite 投影 | `%APPDATA%\QoderWork CN\data\agents.db`（WAL） | 对应 userData/data | 会话列表、消息投影、搜索、任务、memory 元数据 |
| 每次会话状态 | `...\<session-id>\state.json`、`...\compression-v2\state.json` | 同上 | 压缩/恢复元数据 |
| 长期记忆 | `%USERPROFILE%\.qoderworkcn\awareness\main\` | `~/.qoderworkcn/awareness/main/` | `MEMORY.md`、`USER.md`、`memory/YYYY-MM-DD.md`、`.index.sqlite`、`.memory_meta.json` |
| 文件快照/命令 | `.qoderworkcn\file-history\`、`shell-snapshots\`、`workspace\`、`logs\` | 同上 | 编辑回滚、shell 快照、任务产物、运行日志 |

**本机实测规模**：`projects` 下 173 个 JSONL（含子代理），24,072 行，47.7 MB；最大单文件 831 行；另有 402 个 project 侧文件（48.6 MB）、125 个 workspace 文件（53.5 MB）、199 个日志文件（49.9 MB）。[本机观察]

### 1.2 JSONL 条目类型（实测聚合）

对 173 个 JSONL、24,072 行做聚合，`type` 只有 6 种：

| type | 数量 | 关键字段 |
|---|---:|---|
| `assistant` | 12,731 | `uuid,parentUuid,message,agentId,parent_tool_use_id,sessionId,session_id,timestamp,cwd,isSidechain,version` |
| `user` | 8,936 | `uuid,parentUuid,message,origin,promptId,permissionMode,sourceToolAssistantUUID,toolUseResult,isMeta,isVisibleInTranscriptOnly,isCompactSummary` |
| `system` | 1,892 | `uuid,parentUuid,subtype,content,level,isCompactSummary,compactMetadata,logicalParentUuid` |
| `last-prompt` | 247 | `lastPrompt,sessionId` |
| `file-history-snapshot` | 136 | `messageId,snapshot,isSnapshotUpdate` |
| `runtime-config` | 130 | `sessionId,model,reasoningEffort,contextWindow,timestamp` |

脱敏样例：

```json
{"type":"runtime-config","sessionId":"<uuid>","model":"<model>","reasoningEffort":null,"contextWindow":null,"timestamp":<ms>}
{"type":"user","uuid":"<uuid>","parentUuid":"<uuid>","message":{"role":"user","content":[{"type":"text","text":"<text>"}]},"sessionId":"<uuid>","cwd":"<cwd>","version":"<version>"}
{"type":"assistant","uuid":"<uuid>","parentUuid":"<uuid>","message":{"id":"<id>","type":"message","role":"assistant","model":"<model>","content":[{"type":"text","text":"<text>"}]},"sessionId":"<uuid>"}
```

这基本是 **Claude Code transcript 的 Qoder 变体**：`parentUuid` 串消息，`user` 里带 `toolUseResult`，`assistant` 里带 `parent_tool_use_id`，另有 `runtime-config` 和 Qoder 专有的 `system.subtype`。

### 1.3 消息怎么串、删中间会不会断

- 主链是 `parentUuid -> uuid`；`last-prompt` 记录最近输入，没有 Claude 那种 `leafUuid` 字段（Qoder 用 `sessionId`）。
- `system` 的 compact boundary 用 `parentUuid: null` + `logicalParentUuid` 指向压缩前节点；普通消息仍有 `parentUuid`。
- 物理删除中间一条会产生两类问题：
  1. 子条目的 `parentUuid` 指向删除的 uuid；
  2. SQLite 投影按 `sequence` 连续索引（`messages_sub_chat_sequence_unique`），删行后会留下 gap。
- Qoder 代码里没有“删一条用户消息”的通用 UI 函数；只有：
  - `deleteMessageById`：只用于 **assistant 投影回滚**（`deleteAssistantMessage`），不是用户删除；
  - `truncateAfterSequence`：按 sequence 删除后缀，用于 **edit/retry**（代码在 3565594 附近设置 `shouldResume:true`），不是删中间一条；
  - `replaceMessagesBySubChat`：事务内删掉整个 subchat 的投影再重建，用于重投影/导入。

### 1.4 SQLite 投影的真实结构

本机 `agents.db`：15 个 chat、15 个 sub_chat、142 条 messages（71 user / 71 assistant），全部 `search_status=ready`，sequence 无 gap。表结构关键点：

- `messages(id, message_id, chat_id, sub_chat_id, sequence, role, parts, metadata, searchable_text, search_status, created_at, updated_at)`
  - `parts` JSON：`text` 或 tool call（`toolCallId/toolName/input/state/result/output`）；
  - `metadata` JSON：`sessionId`、`sdkMessageUuid`、`durationMs`、`numTurns` 等；
  - 唯一约束：`(sub_chat_id, message_id)`、`(sub_chat_id, sequence)`。
- `sub_chats.messages` 列**存在但本机 15 行全部是 `[]`**；当前版本不再在这里镜像消息，早前“JSON 聚合也是副本”的判断需要修正。
- FTS5 使用 `trigram`，且有 **AFTER INSERT / AFTER UPDATE OF searchable_text / AFTER DELETE** 三个触发器：
  - 删除 `messages` 行会自动删除 `messages_fts` 对应行；
  - 所以 FTS 不是“删不掉的第二份”，真正的外部副本是 JSONL、memory、日志。

**代码证据**（`out/main/main.js`）：

- Qoder 的 DB 初始化使用 `better-sqlite3` + `drizzle`，路径 `userData/data/agents.db`。
- `replaceMessagesBySubChat`：`delete(messages).where(subChatId)` 后逐条 `appendMessageWithDb`，事务内重建 sequence。
- `backfillFromSdkTranscript`：当 DB 投影数小于 SDK transcript 时，把 SDK 中“缺的”消息 `appendMissingMessagesBySubChat` 补回 DB。
- `softDeleteChat`：先 `cleanupAwarenessForDelete(subChatIds)`，再把 `chats.deleted_at` 置为当前时间；**没有删除 `projects/<session>.jsonl`**。
- 没有找到用户级的“永久删除 chat”函数。代码里唯一的硬删是内部 `bad xiaoq chats` 修复路径：同样只 `cleanupAwarenessForDelete` + `delete(chats)`，**没有 transcript unlink**。
- `deleteMessageById`：只按 `(sub_chat_id,message_id)` 删投影；调用者是 assistant projection 的 `deleteAssistantMessage()`。
- `truncateAfterSequence`：按 `(sub_chat_id, sequence > X)` 删投影；调用者是重试/编辑路径。

### 1.5 压缩（compaction）真实结构

Qoder transcript 里存在：

```json
{"type":"system","subtype":"compact_boundary","isCompactSummary":true,
 "content":"<summary>","logicalParentUuid":"<uuid>","parentUuid":null,
 "compactMetadata":{"trigger":"<trigger>","preTokens":<n>,"messagesSummarized":<n>,"postTokens":<n>,"durationMs":<n>}}
```

以及 `user` 的 `isCompactSummary:true / isVisibleInTranscriptOnly:true` 摘要消息；其 `content` 是 text block。`compression-v2/state.json` 保存：

- `replacementDecisions`（替换决策）
- `seenFunctionResponseIds`
- `sessionMemoryState`
- `autoCompactTracking`（`consecutiveFailures` / `lastCompressionStatus`）
- `snippedMessageIds`（被剪掉的消息 ID）

这说明 Qoder 的压缩不是“删旧行”，而是：
1. 追加 compact_boundary + summary；
2. 用 `logicalParentUuid` 接回压缩前节点；
3. 用 `compression-v2` 记录哪些消息被替换/剪掉；
4. 原始 JSONL 行仍在。

### 1.6 恢复 / 删除语义

- 恢复时 SDK 读 `<session-id>.jsonl`；DB 是投影，`backfillFromSdkTranscript` 会在投影缺失时从 transcript 补回。**因此只删 DB 行，恢复/打开会话时可能被 transcript 补回。**
- `deleteChat` 是软删：DB `deleted_at` + 清 memory 中带 chat 标记的 block；transcript 未删。若要真正清除，必须另行删 `projects/*.jsonl`、`compression-v2`、subagents、file-history、logs、workspace，且要在 SDK 不占用会话时做。
- 官方 UI 是否有“删单条消息”：**本机代码没有找到**；只有会话级删除/归档、edit/retry（截断后缀）、assistant 投影回滚。
- 校验：JSONL 无 hash/签名；DB 有唯一索引和 FTS trigger；恢复不校验内容 hash。

### 1.7 会话之外的真实副本

| 位置 | 实测/代码 |
|---|---|
| `~/.qoderworkcn/awareness/main/` | `MEMORY.md` 5.9KB、`USER.md` 2.9KB、`.index.sqlite` 716KB、`.memory_meta.json`、`.hash-state.json`、`memory/2026-*.md`；一天文件里有 14 个 `memory-chat:` 标记 → 记忆按 chat 分块。删 chat 的代码会按 chat 删除这些 block，但**单条消息删除不会自动清 memory**。[本机观察 + `cleanupAwarenessForDelete`] |
| `~/.qoderworkcn/file-history/` | 35 个快照文件，593KB；编辑回滚用。[本机观察] |
| `~/.qoderworkcn/shell-snapshots/` | 3 个 shell 快照。[本机观察] |
| `~/.qoderworkcn/logs/` | 199 个文件，49.9MB；含 `qoder-agent-sdk.log`（39MB，260,199 个 `QueryRunner` 标记、3,904 个 `assistant`、4,049 个 `user`），是完整的 SDK 协议日志。[本机观察] |
| `~/.qoderworkcn/workspace/` | 125 个文件，53.5MB；任务产物。[本机观察] |
| `~/.qoderworkcn/projects/` | 173 个 JSONL（含子代理），47.7MB；删 chat 未发现 unlink。[本机观察 + 源码] |
| SQLite WAL / FTS | `agents.db-wal/shm` + `messages_fts`；FTS 有 delete trigger，但 WAL 中可能保留旧页直到 checkpoint。[本机观察] |

### 1.8 保留 / 清理

- 源码里只有日志清理：`LOG_RETENTION_DAYS=7`，但 `cleanupOldLogs` 仅在 `CLAUDE_RAW_LOG=1` 时启用；默认日志关闭。
- `chats.deleted_at` 软删；没有找到按天清理 `projects/*.jsonl` 或 `agents.db` 的定时器。
- 结论：会话 JSONL 和 DB 长期累积；删 chat 不会自动清 transcript。

## 2. WorkBuddy 5.8.3.41334564

### 2.1 安装包与源码

- Windows 安装包：`WorkBuddy-win32-x64-user-5.8.3.41334564-db0e9b51.exe`，SHA-256 与官方 `/v2/update` 返回值一致；解包后 `WorkBuddy.exe` 5.8.3；`resources/app.asar` 96.5MB。
- Electron 主进程 + `better-sqlite3`；CLI 运行时 `resources/app.asar/cli/dist/codebuddy-lite-wb.mjs`（CodeBuddy 同源）。
- 本机没有运行 WorkBuddy，所以以下路径/字段来自安装包源码，不是本机数据观察（会标明）。

### 2.2 存储布局

| 层 | 路径/结构 |
|---|---|
| User data | `~/.workbuddy/app`（源码 `resolveUserDataDir()`；可用 `WORKBUDDY_USER_DATA_DIR` 覆盖） |
| SQLite | `workbuddy.db` + `workbuddy.db-wal` + `workbuddy.db-shm`；WAL，启动时做 checkpoint/quick_check/损坏恢复 |
| 会话 metadata 表 | `sessions(id,cwd,user_id,title,custom_title,status,created_at,updated_at,last_activity_at,deleted_at,is_playground,source_mode,is_background_automation,mode,model,expert_id,expert_locale,expert_runtime_identity,expert_marketplace,permission_mode,use_sandbox_cli,project_id)` |
| transcript | `projects/<compressed-cwd>/<session-id>.jsonl`；同目录 `*.meta.json`、`*.file-rollback.ndjson` |
| 其他 | `session-artifacts.json`、`settings.json`、`device-id`、`.policy-cache.json`、`session_usage`、`cloud_conversations`、`workspaces`、`automations` |

`projects/*/*.jsonl`、`*.meta.json`、`*.file-rollback.ndjson` 是安装包 `WORKBUDDY_PLATFORM_OWNED_PROJECT_FILE_PATTERNS` 明确列出的平台文件。

### 2.3 transcript 条目类型

WorkBuddy/CodeBuddy 不是 Claude 的 `parentUuid` 格式；代码里用 `id` / `parentId` / `logicalParentId`：

| type | 关键字段 | 说明 |
|---|---|---|
| `session-meta` | `type:"session-meta", id, meta` | 文件头；`readHeadSessionMeta` 只认这个 type，`meta` 里放会话级信息 |
| `message` | `type:"message", role:"user"|"assistant", content, id, parentId, logicalParentId, timestamp, isSidechain` | 用户/助手消息；`content` 可以是 string 或 block 数组 |
| `function_call` | `type:"function_call", name, arguments, id, parentId` | 工具调用 |
| `function_call_result` | `type:"function_call_result", name, error, ...` | 工具结果 |
| `summary` / `topic` | `type:"summary"|"topic"` | 摘要/主题；`buildTranscriptFromHistory` 显式跳过它们，不进入普通 transcript |
| `file-history-snapshot` | `type:"file-history-snapshot", messageId, snapshot` | 文件快照 |
| compact/replay | `summary` + `isSidechain` + `logicalParentId`；`HistoryUtils.resolveReplayHistory(..., {hasCompactedHistory})` | 压缩/分支重放 |

脱敏样例：

```json
{"type":"session-meta","id":"<uuid>","meta":{"cwd":"<cwd>","title":"<title>","model":"<model>"}}
{"type":"message","id":"<id>","parentId":"<id>","role":"user","content":[{"type":"text","text":"<text>"}]}
{"type":"message","id":"<id>","parentId":"<id>","role":"assistant","content":"<text>"}
{"type":"function_call","id":"<id>","parentId":"<id>","name":"<tool>","arguments":"<json>"}
```

### 2.4 消息怎么串、删中间会不会断

- `walkBranch` 从 tip 沿 `parentId` 回溯；`logicalParentId` 用于 compact/逻辑父节点。
- `resolveTip` 过滤 `session-meta`，调用 `HistoryUtils.resolveReplayHistory`，再取最后一条 `id`。
- 所以删中间一条会断分支：必须把子条目的 `parentId` 改到被删节点的父；如果被删的是 `logicalParentId` 目标，还要改逻辑链。
- 这与 Claude 的 `parentUuid` 同类问题，但字段名和“summary/topic/function_call”类型不同；不能直接复用 Claude 的修复逻辑。

### 2.5 压缩 / 恢复 / 删除

- 压缩/回放：`resolveReplayHistory` 接受 `hasCompactedHistory`；`summary`/`topic` 不进入普通 transcript；代码里有 `compact` 相关恢复分支。具体 compact 条目名/字段没有在安装包内找到独立 schema，**未确认**。
- 恢复：本地 API `GET /api/v1/sessions/:id` / snapshot；`probeSessionMaterialized` 先找 live session，再找 transcript path；`buildSessionSnapshot` 从 transcript 读。`session-meta` 是恢复入口。
- 运行中：有 writer lock / session lock（ACP writer），不会每轮重读；未实测。
- 删除：本地 API `DELETE /api/v1/sessions/{id}`（204；`cwd` 用于清 pin）。**会话级**；没有找到单条消息删除 API。源码里未逐行确认该端点是否物理 `unlink` transcript，**未确认**。
- 云端：DB 有 `cloud_conversations`；本地/云端双模式，云端会话另有服务端副本。

### 2.6 会话之外

- `.codebuddy/`：项目级/用户级 memory、agents、skills、commands；`getAgentMemoryDir` 明确有 user/project/local 三种 scope。
- `file-history/`、`plans/`、`blobs/`（图片/附件）、`usage-data/facets/`（会话摘要，按 session 写 JSON）、`teams/`、`agent-home/channels/*.jsonl`、`agent-home/audit.jsonl`、`logs/`、`backups/`、`session-artifacts.json`、`assistant-display/`、`local_storage/`、`storage/`、`audit-log/`。
- `conversation-report.html` / `startup-report.html`：支持/诊断报告模板，可能带会话上下文；属于潜在副本。

### 2.7 保留

- `sessions.deleted_at` 软删字段；未找到按天自动清理 transcript 的代码；`workbuddy.db` 有 WAL checkpoint 和损坏恢复，但不是保留期策略。**保留期未确认**。

## 3. 千问办公 QwenWork 1.4.0.26102214

### 3.1 它和 QoderWork 是同源实现

安装包 `QwenWorkCN 1.4.0.26102214`（DingTalk 签名）解包后：

- `resources/migrations/0000_mixed_blur.sql` 与 QoderWork 的 migrations **同名同结构**：`chats`、`projects`、`sub_chats`、`sub_chats.messages DEFAULT '[]'`。
- 主进程 `getDatabasePath()`：`app.getPath("userData")/data/agents.db`；`better-sqlite3`。
- 代码里直接引用 `@qoder-ai/qoder-agent-sdk`，`getSessionMessages()` / `forkSession()` / `deleteSession()`；数据根包含 `.qwenworkcn`、`.qoderwork`。
- 有 `CHAT_CONTROL_COMMANDS.COMPACT = "compact"` 和隐藏控制命令 `/compact`。
- `resources/agent-sdk` 里有 `qwencode`、`flash-cli`、`opencode` 适配层；`resources/awareness-templates`、`memory-reflection` 说明也有 awareness memory。

### 3.2 存储结构（源码级）

| 层 | 结构 |
|---|---|
| SQLite | `userData/data/agents.db`（Windows 预期 `%APPDATA%\QwenWorkCN\data\agents.db`，本机未运行，未直接观察）；Qoder 同款 `chats/sub_chats/messages` + FTS |
| SDK transcript | `getSessionMessages` 从 `.qwenworkcn`（fallback `.qoderwork`）目录读取；一个 session 一个 JSONL + subagents |
| 压缩 | `/compact` 控制命令；SDK 侧 compaction（与 Qoder 同源） |
| 记忆 | `awareness-templates` + `memory-reflection`；本地 awareness 目录（没有运行实例，未直接观察） |

### 3.3 删除 / 恢复

- 源码有 `deleteSession`（SDK）用于删除 fork 出来的临时会话；但**没有看到用户级单条消息删除**。
- 本机没有安装/运行 QwenWork，因此没有做实际恢复/删除实验；以下为源码判断：
  - 与 Qoder 一样，SQLite 是投影，SDK transcript 是正文；
  - 只删 DB 投影可能被 `getSessionMessages`/重投影补回；
  - 删会话是 SDK/DB 层动作，JSONL 是否一并删除取决于 `deleteSession` 的 SDK 实现，**未确认**。

### 3.4 官方文档 vs 本机

官方文档把 QwenWork 描述为“工作空间 + Agent 会话、云端工作空间、独立上下文”；桌面端实际仍有本地 `agents.db` + SDK transcript。也就是说：**云端工作空间是产品层，桌面端仍有本地会话缓存/投影**；单条消息删除能力没有在官方文档中承诺。

## 4. 扣子 Coze（桌面 1.1.9 + 云 API + Coze Studio）

### 4.1 桌面端：没有本地会话 DB

- 安装 `Coze 1.1.9` 位于本机；`%APPDATA%\Coze` 里有 `IndexedDB`（约 3KB）、`Local Storage`（约 380KB）、Cache、Session Storage；**没有 SQLite/JSONL 会话库**。
- `app.asar` 主进程只负责 Electron shell、登录、更新、本地文件/命令桥；没有 `better-sqlite3` 会话存储。
- 结论：Coze 桌面端的会话正文在服务端；本地只有浏览器缓存/UI 状态，不能靠改本地文件删消息。

### 4.2 云 API：180 天 + 删除消息

官方文档明确：

- 消息在服务端保存 **180 天**，到期自动删除；可调用删除消息接口。[创建消息](https://docs.coze.cn/developer_guides_create_message)、[删除消息](https://docs.coze.cn/developer_guides_delete_message)
- 消息字段：`id, conversation_id, bot_id, chat_id, role, content, content_type, type, section_id, reasoning_content, created_at, updated_at`。
- `type`：`question / answer / function_call / tool_response / follow_up / verbose`；`content_type`：`text / object_string / card`。
- `section_id` 表示上下文分段；清除上下文会产生新 section。
- 会话级：`conversation_id` + `chat_id`；消息级：`message_id`。

### 4.3 Coze Studio（开源自托管）的真实删除粒度

用 `coze-dev/coze-studio` 源码和 MySQL schema 对照：

- `conversation`：`status 1-normal 2-deleted`；`section_id`。
- `message`：`status 1 Available 2 Deleted 3 Replaced 4 Broken 5 Failed 6 Streaming 7 Pending`；字段 `run_id,conversation_id,user_id,agent_id,role,content_type,content,message_type,display_content,ext,section_id,broken_position,model_content,meta_info,reasoning_content`。
- `DeleteMessage` 的实现不是只删一条：
  1. 按 `message_id` 取消息；
  2. `AgentRunDomainSVC.Delete([]int64{messageInfo.RunID})` 删除整个 run；
  3. `MessageDomainSVC.Delete(&entity.DeleteMeta{RunIDs: []int64{runID}})` 按 run 删除该组消息；
  4. schema 的删除是 `status=2` 软删，不是 `DELETE FROM`。
- 因此：**云 API 的“删除消息”在 Studio 实现里是“删除该消息所属的 run（通常含提问+回答+工具消息）”，且是软删**。云侧是否完全同粒度，未确认；但这是目前能拿到的最强实现证据。

## 5. 飞书 Aily

### 5.1 纯服务端模型

官方 API 把 Aily 分成 Session / Message / Run：

- Session：用户与 Aily 的一次会话；
- Message：文本、表格、图片等多模态内容；
- Run：Aily 基于会话消息做意图判定、调用技能并返回结果。

消息字段（官方 `GET /open-apis/aily/v1/sessions/:aily_session_id/messages`）：

`id, session_id, run_id, content_type, content, files[], quote_message_id, sender, mentions, plain_text, created_at, status`

`status` 可为 `IN_PROGRESS / COMPLETED`；`content_type` 可为 MDX 等。[列出 Aily 消息](https://open.feishu.cn/document/aily-v1/aily_session-aily_message/list.md?lang=zh-CN)

### 5.2 删除能力

- **有删除会话**：`DELETE /open-apis/aily/v1/sessions/:aily_session_id`，权限 `aily:session:write`，返回 `data:{}`。[删除会话](https://open.feishu.cn/document/aily-v1/aily_session/delete.md)
- **没有删除单条消息 API**：官方 API 索引里只有创建/列出/获取消息，没有 message delete；尝试 `aily_session-aily_message/delete.md` 返回 404。
- 所以粒度是**整会话删除**；删除会话是否级联消息/Run、是否软删，API 文档没有展开，**未确认**。

### 5.3 本地 / 保留

- 无本地会话文件；Aily 是飞书开放平台服务端。
- 保留期没有在 API 文档中给出；租户数据保留/审计取决于飞书租户策略，**未确认**。

## 6. MiniMax Code 0.6.5（开源 CLI）

### 6.1 版本与数据目录

- 仓库 `MiniMax-AI/minimax-code` `package.json` 版本 **0.6.5**；桌面端版本未从安装包确认（官方下载页只给 macOS/Windows 安装包，没有版本号）。
- 数据目录：`~/.minimax`（旧版 `~/.mavis` 会自动迁移/兼容链接）；`sessionsDir = ~/.minimax/sessions`；`memory/agents/plans/logs/plugins` 同根。[源码 `packages/config/src/data-dir.ts`、`config.ts:2038`]

### 6.2 两层：SQLite + canonical JSONL

| 层 | 结构 |
|---|---|
| SQLite | `local_runtime_sessions(session_id,record_json,updated_at_ms,agent_name,session_type,status,archived,visibility,session_kind,parent_session_id,workspace_dir,title,history_relative_dir,...)`；`local_runtime_message_rows(session_id,msg_id,role,turn_id,source,data_json,...)`；`local_runtime_session_locks` |
| JSONL | `~/.minimax/v2/sessions/YYYY/MM/DD/<time>-<encoded-session-id>/` 下 `manifest.json`、`messages.jsonl`、`ledger.jsonl`、`display.jsonl`、`snapshot.json`、`snapshots/`、`reports/` |
| 历史信封 | `{message_id, turn_id, message, turn_config?, history_artifact?}`；`message` 是带 `role/timestamp` 的消息，或 `{role:"compactionSummary", summary}` |

`messages.jsonl` 是 canonical history；`turn_config` 只允许出现在 user 消息上，包含 `system_prompt/model/tools`；`history_artifact` 指向快照/产物。revision 用**递归 key 排序的 SHA-256**，`snapshots/g000000000000--before.jsonl` 形成代际链，父代必须匹配 `generation-1` 和 `compactionId`。

### 6.3 压缩 / 恢复 / 删除

- 压缩：`compactionSummary` 角色 + snapshot 链；`canonicalHistoryScanner` 校验 `parentSnapshot`、`generation`、`revision`，不匹配就报 `parent-snapshot-missing` / `artifact-revision-mismatch`。
- 恢复：SQLite session 记录 + canonical JSONL；`session-history-location` 解析 manifest/legacy layout；有 `local_runtime_session_locks`，运行中加锁。
- 删除：`deleteSessionHistory(dataDir, session)` 会 `rmSync(sessionDir,{recursive:true})`，并校验路径必须在 `v2/sessions` 下、manifest 身份匹配。**这是真物理删除会话目录**。
- 单条消息删除：没有找到 `deleteMessage` 级 API；消息行/JSONL 是追加/重建模型。UI 文档只承诺归档，不承诺删单条。

### 6.4 会话之外

`~/.minimax` 下还有 `memory/`、`agents/`、`plans/`、`logs/`、`plugins/`、`snapshots/`、`reports/`、observability `mcode-observability-*.jsonl`；以及 `messages.jsonl`、`display.jsonl`、`ledger.jsonl` 多份表示。删会话目录会一起删这些；删单条则要同时处理 SQLite row、messages.jsonl、display.jsonl、snapshots。
